# Migrating from smalldi 0.2 to 0.3

This guide covers the step from 0.2.0 to 0.3.0. The first line of every snippet names the version it runs on; a
snippet that is not runnable on its own is labelled `fragment` there. Upgrading straight to 0.4? Use
[0.2 → 0.4](0.2-to-0.4.md) instead.

## Summary

| Change | Breaking | Action required |
|--------|----------|-----------------|
| `@Injector.singleton` instantiates the class on first use, not when the decorator is applied | yes | Call `Injector.get_instance(T)` where construction at import time was relied on |
| `Injector.singletons_available` is a deprecated read-only snapshot: every read warns, instantiates and freezes every singleton | yes | Replace reads with `Provide[T]` or `Injector.get_instance`, membership tests with `Injector.is_singleton`, swaps with `@Injector.override`; remove `clear()`, `update()` and item assignment |
| Registering the same class twice raises `TypeError` | yes | Register each class once; swap implementations with `@Injector.override` |
| `typing-extensions` is not a dependency of smalldi | yes, if your code imports it | Declare it in your own dependencies |
| `@Injector.inject` resolves `Provide[T]` at every call instead of capturing instances at decoration | no | None, unless code relied on the captured instance |
| A `Container` is instantiated when its first component is registered | no | Override a container before registering components |
| Interfaces, overrides, `Injector.get_instance`, `SingletonFrozenError`, `smalldi.concurrency`, `smalldi.decorator` | no | Optional, see [New features you can adopt](#new-features-you-can-adopt) |

## Breaking changes

### `@Injector.singleton` instantiates the class on first use

**What changed**: In 0.2.0 the decorator calls the class and stores the instance, so the constructor runs while the
module is imported. In 0.3.0 the decorator only registers the class; the constructor runs the first time an
instance is requested, through an injected `Provide[T]` parameter, `Injector.get_instance(T)` or a read of
`Injector.singletons_available`, and at most once.

**How to find affected code**: `@Injector\.singleton` lists every registration, and `Injector\.singleton\(` the
function-call form. Inspect each registered class's `__init__` for side effects that were expected at import time
(opening connections, registering handlers, printing) and for exceptions that were expected to fail the import.

**Before** (0.2.0):

```python
# smalldi 0.2.0
from smalldi import Injector


@Injector.singleton
class CookieJar:
    def __init__(self):
        print("CookieJar filled")  # runs while the decorator is applied


print("Pusheen arrives")
# Output: "CookieJar filled", then "Pusheen arrives"
```

**After** (0.3.0):

```python
# smalldi 0.3.0
from smalldi import Injector


@Injector.singleton
class CookieJar:
    def __init__(self):
        print("CookieJar filled")  # runs at the first request, not at import


print("Pusheen arrives")
Injector.get_instance(CookieJar)  # fill the jar at startup instead of at the first injection
# Output: "Pusheen arrives", then "CookieJar filled"
```

**How to verify**: Import the modules that register singletons and confirm the side effects did not happen yet;
call `Injector.get_instance(T)` for each class that needs eager construction and confirm they happen once. A
constructor that raises does so at that call, not at import, so startup code that catches import errors must catch
them there.

### `Injector.singletons_available` is a deprecated read-only snapshot

**What changed**: In 0.2.0 `Injector.singletons_available` is the registry itself, a plain `dict` mapping each
registered class to its instance, which user code can read, write and clear. In 0.3.0 every read emits a
`DeprecationWarning`, instantiates every registered singleton that has no instance yet, freezes all of them so
none can be overridden afterwards, and returns a `types.MappingProxyType`: item assignment raises `TypeError`, and
`clear()` and `update()` do not exist on it. Interfaces are not included. The attribute is removed no earlier
than 1.0.0.

**How to find affected code**: `singletons_available\[` finds reads and writes by key;
`singletons_available\.(clear|update|copy|pop|setdefault|get|items|keys|values)` finds dict operations, typically in
test fixtures; `in Injector\.singletons_available` finds membership tests; `singletons_available` on its own
finds everything else.

**Before** (0.2.0):

```python
# smalldi 0.2.0
from smalldi import Injector


@Injector.singleton
class CookieJar:
    cookies = 3


class EmptyCookieJar(CookieJar):
    cookies = 0


print(CookieJar in Injector.singletons_available)        # True
print(Injector.singletons_available[CookieJar].cookies)  # 3
Injector.singletons_available[CookieJar] = EmptyCookieJar()  # swap the instance, for a test
print(Injector.singletons_available[CookieJar].cookies)  # 0
```

**After** (0.3.0):

```python
# smalldi 0.3.0
from smalldi import Injector


@Injector.singleton
class CookieJar:
    cookies = 3


@Injector.override(CookieJar)  # declared before the first request for CookieJar
@Injector.singleton
class EmptyCookieJar(CookieJar):
    cookies = 0


print(Injector.is_singleton(CookieJar))            # True
print(Injector.get_instance(CookieJar).cookies)    # 0
```

**How to verify**: Run the test suite with `python -W error::DeprecationWarning -m pytest`: every remaining read
of `Injector.singletons_available` fails the test that performs it. Item assignment fails with `TypeError`, and
`clear()` or `update()` with `AttributeError`, so a fixture that resets the registry this way fails at its first
use.

### Registering the same class twice raises `TypeError`

**What changed**: In 0.2.0 applying `Injector.singleton` to an already registered class replaces its instance
with a new one. In 0.3.0 it raises `TypeError` and the registration is left unchanged.

**How to find affected code**: `Injector\.singleton\(` finds the function-call form, which is how a class is
registered a second time on purpose; `importlib\.reload\(` finds module reloads, which define new class objects
that are registered next to the old ones and are not supported.

**Before** (0.2.0):

```python
# smalldi 0.2.0
from smalldi import Injector


class CookieJar:
    def __init__(self):
        self.cookies = 3


Injector.singleton(CookieJar)
Injector.singletons_available[CookieJar].cookies = 0
Injector.singleton(CookieJar)  # registers again: a fresh, full jar replaces the empty one
print(Injector.singletons_available[CookieJar].cookies)  # 3
```

**After** (0.3.0):

```python
# smalldi 0.3.0
from smalldi import Injector


@Injector.singleton
class CookieJar:
    def __init__(self):
        self.cookies = 3


try:
    Injector.singleton(CookieJar)
except TypeError as error:
    print(type(error).__name__, error)

Injector.get_instance(CookieJar).cookies = 0
print(Injector.get_instance(CookieJar).cookies)  # 0: one registration, one instance
```

**How to verify**: Import every module that registers singletons once in one process; a second registration of
any class raises `TypeError` at import.

### `typing-extensions` is not a dependency of smalldi

**What changed**: 0.2.0 declares `typing-extensions>=4.5` as a dependency, so installing smalldi installs it.
0.3.0 declares no dependencies.

**How to find affected code**: `typing_extensions` over your code and `typing-extensions` over your dependency
declarations. Code that imports it without declaring it breaks in a fresh environment.

**Before** (0.2.0):

```python
# fragment: typing-extensions is installed with smalldi 0.2.0, so this import works without a declaration
from typing_extensions import Self
```

**After** (0.3.0):

```toml
# fragment: declare the dependency yourself, in pyproject.toml
[project]
dependencies = ["typing-extensions>=4.5"]
```

**How to verify**: Install your project into a fresh virtual environment and import every module; a missing
`typing_extensions` raises `ModuleNotFoundError`.

## Behaviour changes without API changes

### `@Injector.inject` resolves `Provide[T]` at every call

**What changed**: In 0.2.0 the decorator looks each `Provide[T]` up when it is applied and injects that captured
instance on every call. In 0.3.0 the decorator only checks that each `T` is registered, and every call asks
`Injector.get_instance(T)`, so an override declared after decoration and before the first call is injected, and
the instance is created by the first call.

**How to find affected code**: `@Injector\.inject` lists every injected function. Affected are those that rely on
the instance captured at decoration staying in effect after the registry changed.

**Before** (0.2.0):

```python
# smalldi 0.2.0
from smalldi import Injector, Provide


@Injector.singleton
class CookieJar:
    cookies = 3


@Injector.inject
def count_cookies(jar: Provide[CookieJar]) -> int:
    return jar.cookies


class EmptyCookieJar(CookieJar):
    cookies = 0


Injector.singletons_available[CookieJar] = EmptyCookieJar()
print(count_cookies())  # 3: the instance captured at decoration
```

**After** (0.3.0):

```python
# smalldi 0.3.0
from smalldi import Injector, Provide


@Injector.singleton
class CookieJar:
    cookies = 3


@Injector.inject
def count_cookies(jar: Provide[CookieJar]) -> int:
    return jar.cookies


@Injector.override(CookieJar)  # after the decoration, before the first call
@Injector.singleton
class EmptyCookieJar(CookieJar):
    cookies = 0


print(count_cookies())  # 0: resolved at the call
```

**How to verify**: Declare an override after decorating a function and before calling it; the call receives the
override's instance. `T` must still be registered when the function is decorated, otherwise `TypeError` is
raised there.

### A `Container` is instantiated when its first component is registered

**What changed**: In 0.2.0 a container subclass is instantiated by `@Injector.singleton`, like any singleton. In
0.3.0 the first `@SnackBowl.component` registration requests the container through `Injector.get_instance`,
which creates the instance and freezes the container, so a container can be overridden only before any component
is registered, and components registered in an overridden container go to the override's instance.

**How to find affected code**: `\(Container\)` finds container subclasses and `\.component\b` their
registrations. Affected are containers whose constructor has side effects, and overrides of containers declared
after a component registration.

**Before** (0.2.0):

```python
# smalldi 0.2.0
from smalldi import Injector
from smalldi.container import Container


@Injector.singleton
class SnackBowl(Container):
    def __init__(self):
        super().__init__()
        print("SnackBowl set out")  # at the decoration


print("Pusheen arrives")


@SnackBowl.component
def cookie():
    return "cookie"


print([registration.component.__name__ for registration in Injector.singletons_available[SnackBowl].components])
```

**After** (0.3.0):

```python
# smalldi 0.3.0
from smalldi import Injector
from smalldi.container import Container


@Injector.singleton
class SnackBowl(Container):
    def __init__(self):
        super().__init__()
        print("SnackBowl set out")  # at the first component registration


print("Pusheen arrives")


@SnackBowl.component
def cookie():
    return "cookie"


print([registration.component.__name__ for registration in Injector.get_instance(SnackBowl).components])
```

**How to verify**: Register a component and confirm the container's constructor ran once at that point; an
override of the container declared after it raises `SingletonFrozenError`.

## New features you can adopt

* Interfaces: `@Injector.interface` registers an abstract class, `@Injector.implements(Interface)` declares its one
  implementation and `Provide[Interface]` injects it. See [README: Interfaces](../../README.md#interfaces).
* Overrides: `@Injector.override(Target, when=...)` injects a registered singleton instead of another singleton or
  an interface's implementation, with the non-transitivity and freezing rules.
  See [README: Overrides](../../README.md#overrides).
* `Injector.get_instance(T)`, `Injector.is_singleton(cls)` and `Injector.is_interface(cls)` replace every use of the
  registry dict. See [README: Injector](../../README.md#injector).
* `SingletonFrozenError`, exported from `smalldi`, is raised by an override of a frozen target.
* `smalldi.concurrency`: `@synchronized`, `@threadsafe` and `mutex(lock)`.
  See [README: Concurrency](../../README.md#concurrency).
* `smalldi.decorator.staticclass`; `smalldi.wrappers` keeps working as an alias.
* `smalldi.atomic.AtomicSet`, a set whose operations are serialized by a lock.
* Thread safety: each singleton is constructed at most once across threads, and a circular dependency within one
  thread raises `RuntimeError`. See [README: How singletons work](../../README.md#how-singletons-work).

## Private internals

In 0.2.0 the registry dict is the public `Injector.singletons_available`. In 0.3.0 the registry is the private
class attribute `Injector._singletons_available`, a `dict` of `LazySingleton` objects, next to
`Injector._interface_resolver`; both are implementation details that 0.4.0 does not have (see
[0.3 → 0.4: Private internals](0.3-to-0.4.md#private-internals)). Do not clear or copy them in test fixtures.
0.3.0 has no public way to clear the registry: a test double is declared with `@Injector.override(Target)` above
`@Injector.singleton` before the first injection of `Target`, and `when=` makes the override conditional.

## Checklist

- [ ] Search for `@Injector\.singleton` and `Injector\.singleton\(`; call `Injector.get_instance(T)` at startup for every class whose constructor must run at import time, and move import-time error handling to that call.
- [ ] Search for `singletons_available\[`, `singletons_available\.(clear|update|copy|pop|setdefault|get|items|keys|values)` and `in Injector\.singletons_available`; replace reads with `Provide[T]` or `Injector.get_instance(T)`, membership tests with `Injector.is_singleton(T)`, and instance swaps with `@Injector.override(T)` declared before the first request.
- [ ] Remove registry-clearing test fixtures; declare test doubles with `@Injector.override(T, when=...)` instead.
- [ ] Search for `Injector\.singleton\(` and `importlib\.reload\(`; make sure each class is registered once per process.
- [ ] Search for `typing_extensions`; declare `typing-extensions` in your own dependencies if it is imported.
- [ ] Search for `@Injector\.inject`; check for code that relies on the instance captured at decoration.
- [ ] Search for `\(Container\)` and `\.component\b`; move container overrides before the first component registration and container constructor side effects to where the first registration happens.
- [ ] Run the test suite with `python -W error::DeprecationWarning -m pytest`.
